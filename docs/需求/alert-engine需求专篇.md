## 0. 完成情况总览

> 一句话：**共 35 条需求，全部 ⏳**（本专篇为立项，尚未开工）。
> **本引擎是十个引擎里"家底最薄"的一个**：今天它只是一个数组加一个 10 条上限。

**现有资产映射**

| 现有实现 | 位置 | 已有 | 缺什么 |
|---|---|---|---|
| `alert` 事件 | 契约 §4 | 事件名与方向的约定 | 没有产生者 |
| 前端 `alerts` 数组 | `frontend/src/stores/useStore.ts` L71、L180、L607–611 | `applyWs` 的 `alert` case：`[{...a}, ...s.alerts].slice(0, 20)` | **只是一个 20 条上限的数组**：无规则、无分级、无去重、无确认、无持久化 |
| 告警浮层 | `frontend/src/features/AlertToasts.tsx`（4.3 KB） | 展示 | 无逻辑 |
| 左侧导航【告警】 | `AppShell.tsx`；`LeftNavKey` 含 `'alert'`（`useStore.ts` L13） | 导航项存在 | **点进去没有内容源**（没有告警列表接口） |
| 失联检测 | `backend/src/net/Telemetry.cc`（12.4 KB） | UDP 心跳与失联判定（`TR-MSG-03` 已标 ✅） | 失联**结果没有变成告警**，只是事件 |
| 风险预警次数 | `mission_metrics.alert_count` | 一个统计字段（报告里有"风险预警次数"） | **这个计数从哪来，今天没有逻辑** |
| 各类"提示" | `ai.event` 广播（如 `Api.cc` `targetAction` 的 track/watch） | 文本提示 | 提示 ≠ 告警：没有级别、没有确认、没有台账 |

**关键差距（本专篇主要价值）**

> 1. **左导航有【告警】入口，但没有任何告警台账**——这是需求初稿 §3.3 明确列出的 7 个固定入口之一。
> 2. **报告里有"风险预警次数"指标，但计数逻辑不存在**（`Api.cc` `createReport` 只是读 `mission_metrics.alert_count`，谁写进去的没有实现）。
> 3. **失联检测已经能判定了，但结果没变成告警**——`TR-MSG-03` 标 ✅ 而告警链是空的。
> 4. **没有去重**：一个节点失联 3 秒内会持续触发，前端数组会被同一条刷满（20 条上限全是一条）。

## 1. 定位与边界

### 1.1 定位

```
输入：各引擎的状态变更（phase / resource / topology / entity-ledger）+ 宿主探针
   │
   ▼
┌──────────────────────────────────────────────────────────┐
│  alert-engine（C++，无 Web 框架、无 SQL）                  │
│  RULE 规则求值 → GEN 产生 → LEVEL 分级 → DEDUP 去重合并 →   │
│  ACK 确认/消音 → SUB 订阅分发 → AUDIT 审计                  │
│                      │                                   │
│                      └──► 出口：IAlertSink（宿主实现）       │
└──────────────────────┬───────────────────────────────────┘
                       │ alert 事件 + 告警台账
                       ▼
   宿主：落库 + 广播 ｜ 报告引擎：读"风险预警次数" ｜ 界面：浮层与告警列表
```

**一句话**：alert-engine 回答"**现在有没有需要人看的事、多严重、看过没有**"。
它**不推送**（`realtime-hub` 推）、**不画 UI**（宿主浮层）、**不含具体告警规则**（规则是数据）。

### 1.2 为什么必须是独立引擎

1. **告警规则会变，机制不会**：换一套系统，阈值与规则不同，但**分级/去重/合并/确认/审计机制相同**。
2. **它是唯一能防止刷屏的地方**：去重与合并必须在产生侧做，前端做不了（前端看不到全量）。
3. **它被 `report-engine` 依赖**：报告需要"风险预警次数"，必须有权威计数源。
4. **它是异常处理的统一出口**：初稿 §10.8 的异常（失联、链路中断、节点故障、自检不通过）都该落到同一个告警台账。

### 1.3 范围边界

| 做 | 不做 |
|---|---|
| 规则求值（阈值、持续时间、条件组合），规则由数据注入 | 🚫 不含任何具体规则（阈值、持续时间属规则包） |
| 告警产生、分级（至少三级 + 可扩展） | 🚫 不做推送（`realtime-hub` / `EventHub`，走 `IAlertSink`） |
| **去重与合并**（同一实体同一规则在窗口内合并计数） | 🚫 不做界面（宿主浮层与列表） |
| 确认 / 消音 / 关闭 / 重新打开，含操作留痕 | 🚫 不做权限判断（`auth-access`，本引擎只记录操作者 id） |
| 告警台账与查询（按级别/实体/时间/状态） | 🚫 不做通知渠道（短信/邮件等，本项目无需求） |
| 订阅式分发（订阅者按规则/级别过滤） | 🚫 不做业务判断（"这个告警该怎么处理"不在引擎内） |
| 抑制/依赖（父告警存在时抑制子告警） | 🚫 不做自动处置动作 |

### 1.4 硬约束

| 约束 | 取值 | 依据 |
|---|---|---|
| 事件名 | `alert`；负载由本引擎定义但 **MUST 向后兼容现有前端消费**（前端按 `AlertEvent` 读取并插入数组头部） | 契约 §4；`useStore.ts` L607–611 |
| 现有前端行为 | 前端**保留** 20 条内存上限（界面行为）；引擎侧台账 MUST NOT 受此限制 | `useStore.ts` L609 |
| 导航项 | 左侧导航【告警】为固定入口（7 项之一），需要可查询的告警台账支撑 | 初稿 §3.3；`useStore.ts` L13 |
| 报告指标 | `mission_metrics.alert_count`（风险预警次数）MUST 由本引擎提供权威计数 | `Api.cc` L876 |
| 时间戳 | epoch 毫秒；展示用本地时间串 | 契约 §2 |
| 互斥语义 | 确认类动作 MUST 幂等；重复确认 MUST NOT 报错（对齐 `code=1002` 语义与 `confirmPlan` 的做法） | 契约 §2；`Api.cc` L628–630 |
| 语言/构建 | C++17 + CMake ≥ 3.20；仅 `nlohmann/json` | 对齐既有 C++ 模块 |

## 3. 功能需求条目

### 3.1 告警规则（ALT-RULE）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ALT-RULE-01 | **MUST** 规则由**数据**声明（规则 id、触发条件、级别、去重窗口、合并策略、抑制关系），引擎 MUST NOT 内建任何业务规则 | 换一份规则即换告警行为；全仓检索具体阈值零命中 | ⏳ |
| ALT-RULE-02 | **MUST** 规则条件支持：阈值比较、持续时间（"持续 N 秒才报"）、布尔组合、缺失/恢复（"恢复时也报一条"） | 四类条件各有一条用例通过 | ⏳ |
| ALT-RULE-03 | **MUST** 规则装载时校验（重复 id、未知字段、非法窗口），失败给可读原因 | 给一份坏规则 → 装载失败并指出位置 | ⏳ |
| ALT-RULE-04 | **MUST** 规则可运行时启用/禁用，不影响已产生告警 | 禁用后不再产生新告警；历史告警仍可查 | ⏳ |
| ALT-RULE-05 | **SHOULD** 规则版本化：规则集有版本，告警记录 MUST 携带产生时的规则版本 | 可从告警反查当时规则 | ⏳ |

### 3.2 产生与分级（ALT-GEN）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ALT-GEN-01 | **MUST** 产生接口为结构化输入（`{规则id, 实体?, 指标, 数值, 时间, 上下文}`），引擎 MUST NOT 接受"成句文案"作为主要字段 | 引擎不产出自然语言；文案由规则模板或 `llm-provider` 生成 | ⏳ |
| ALT-GEN-02 | **MUST** 级别由规则决定，取值可扩展；MUST NOT 硬编码三级 | 新增一个级别只需改规则 | ⏳ |
| ALT-GEN-03 | **MUST** 幂等锚点：同一（规则 + 实体）在同一去重窗口内的重复触发 MUST 归并为同一条告警并累加计数 | 3 秒内触发 10 次 → 一条告警、计数 10 | ⏳ |
| ALT-GEN-04 | **MUST** 恢复语义：条件不再满足时 MUST 产生"恢复"记录或关闭告警（按规则声明），并可与原告警关联 | 触发→恢复→再触发，三条记录关系正确 | ⏳ |
| ALT-GEN-05 | **MUST** 计数准确：`alert_count` 口径显式（"产生的告警条数"还是"去重后条数"），供报告直接使用 | 口径可复算；与报告显示一致 | ⏳ |
| ALT-GEN-06 | **SHOULD** 首次触发与后续累加可分：可查询"第一次发生时间"与"最近一次时间" | 两个时间可分别读出 | ⏳ |

### 3.3 去重、合并与抑制（ALT-DEDUP）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ALT-DEDUP-01 | **MUST** 去重窗口可配（按规则）；窗口内合并，窗口外新开一条 | 跨窗口触发产生两条 | ⏳ |
| ALT-DEDUP-02 | **MUST** 合并时更新"计数 + 最近时间 + 最新数值"，不改首次时间与原始级别（升级除外，见 ALT-DEDUP-04） | 合并后字段变化符合约定 | ⏳ |
| ALT-DEDUP-03 | **MUST** 抖动抑制：指标在阈值附近震荡时 MUST NOT 产生告警风暴（与 `topology` 的迟滞同理，参数可配） | 构造震荡输入 → 告警条数受控 | ⏳ |
| ALT-DEDUP-04 | **MUST** 升级语义：合并中级别升高 MUST 记录升级事件并保留原级别历史 | 升级可追溯 | ⏳ |
| ALT-DEDUP-05 | **MUST** 抑制关系：父告警存在时可抑制子告警（如"节点失联"抑制该节点的"链路质量差"） | 配置抑制后子告警不产生；父告警关闭后子告警恢复产生 | ⏳ |
| ALT-DEDUP-06 | **SHOULD** 风暴保护：单位时间告警条数超上限时 MUST 触发"汇总告警"并如实上报被折叠条数 | 故意打风暴 → 得到汇总告警与被折叠计数 | ⏳ |

### 3.4 确认与生命周期（ALT-ACK）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ALT-ACK-01 | **MUST** 状态机：`active → acknowledged → closed`，可 `reopen`；非法迁移 MUST 被拒绝 | 非法迁移给可读原因 | ⏳ |
| ALT-ACK-02 | **MUST** 确认幂等：重复确认 MUST 返回成功并标注"已确认"（**MUST NOT 报错**，对齐现有 `confirmPlan` 的做法） | 连点两次不报错 | ⏳ |
| ALT-ACK-03 | **MUST** 操作留痕：确认/关闭/重开 MUST 记录操作者与时间（操作者 id 由宿主注入） | 审计可复原 | ⏳ |
| ALT-ACK-04 | **MUST** 消音：可临时抑制某规则或某实体的告警（有时限），到期自动恢复 | 消音期间不产生；到期后恢复 | ⏳ |
| ALT-ACK-05 | **SHOULD** 自动关闭：条件恢复时按规则自动关闭并留痕 | 行为符合规则声明 | ⏳ |

### 3.5 台账与订阅（ALT-SUB）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ALT-SUB-01 | **MUST** 台账查询：按级别 / 实体 / 时间区间 / 状态筛选，支持分页与超限截断（不静默丢） | 各筛选条件组合正确 | ⏳ |
| ALT-SUB-02 | **MUST** 与任务维度关联：告警 MUST 可归属到任务（供报告与 T7 复盘） | 按任务筛选正确 | ⏳ |
| ALT-SUB-03 | **MUST** 订阅式分发：订阅者可声明关心的规则/级别/实体，引擎只推匹配项 | 订阅过滤生效，不匹配不推 | ⏳ |
| ALT-SUB-04 | **MUST** 出口为反向接口：`IAlertSink`（告警产生/变更）由宿主实现用于落库与广播 | 引擎内无落库与广播 | ⏳ |
| ALT-SUB-05 | **SHOULD** 批量输出：新客户端接入时可一次拉取当前活动告警（不是逐条推送） | 一次调用返回全部活动告警 | ⏳ |
| ALT-SUB-06 | **SHOULD** 与 `realtime-hub` 的兼容：`alert` 事件负载 MUST 保持前端现有字段可读 | 前端 `applyWs` 的 alert case 零改动即可工作 | ⏳ |

### 3.6 非功能性（ALT-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| ALT-NFR-01 | **MUST** 零外部依赖：无 Web 框架、无 SQL（持久化走注入的 `IAlertStore`）；不依赖其它引擎内部 | 空环境独立构建；跨仓 import 零命中 | ⏳ |
| ALT-NFR-02 | **MUST** 时间可注入（`IClock`），使去重窗口与持续时间测试完全可复现 | 注入假时钟测试通过 | ⏳ |
| ALT-NFR-03 | **MUST** 确定性：同输入序列同输出（含去重与合并） | 同序列跑两次结果一致 | ⏳ |
| ALT-NFR-04 | **MUST** 线程安全：多线程产生告警不丢不重 | 并发压测后计数准确 | ⏳ |
| ALT-NFR-05 | **MUST** 独立交付：独立构建、独立示例、独立测试、独立验收脚本（退出码 0/1） | 空环境 clone → 一条命令构建 → 一条命令验收 | ⏳ |
| ALT-NFR-06 | **SHOULD** 性能：1000 条/秒产生压力下去重与分发 P95 ≤ 1 ms | 实测达标 | ⏳ |
| ALT-NFR-07 | **SHOULD** 台账有界：活动告警上限与历史保留期可配 | 长期运行内存与台账不无界增长 | ⏳ |

## 4. 引擎与规则的划分（policies）

| 属引擎（可复用） | 属规则（`policies/mapapp`，项目专属） |
|---|---|
| 规则求值框架（阈值/持续/组合/恢复） | **具体规则**：节点失联 3s、链路受限持续 5s、目标进入高危区 … |
| 产生、分级机制、幂等锚点 | **级别取值与名称**（信息/警告/严重）、配色语义 |
| 去重窗口、合并、抖动抑制、升级 | **各规则的去重窗口与抑制参数** |
| 抑制关系框架、风暴保护 | **父告警 → 子告警的抑制表** |
| 确认/关闭/重开状态机、消音 | **自动关闭策略**、消音默认时长 |
| 台账查询、订阅过滤、批量输出 | **告警文案模板**（"节点 X 失联"） |
| 出口接口、计数口径的**实现** | **`alert_count` 口径取值**（条数 or 去重条数） |

**判据**：引擎公开接口里出现 `失联 3 秒`、`链路受限`、`高危区` 即破线。

## 5. 决策记录

| 编号 | 议题 | 决策 | 影响 |
|---|---|---|---|
| D1 | 引擎部署侧 | **后端 C++** | 全部条目 |
| D2 | 与 `ai.event` 的关系 | **两者并存但语义不同**：`ai.event` 是"提示/播报"（无台账、无确认），`alert` 是"需处置的告警"（有台账）。**MUST NOT 把提示当告警用**，也 MUST NOT 把告警降级成纯提示 | ALT-GEN-01；现有 `targetAction` 的 track/watch 仍走 `ai.event` |
| D3 | 前端 20 条上限 | **保留**（界面行为）；引擎台账 MUST NOT 受此限制 | ALT-SUB-06 |
| D4 | 文案生成 | 引擎出**结构化数据 + 模板填充**；需要自然语言解释时由 `llm-provider` 增强，**引擎 MUST NOT 依赖 LLM** | ALT-GEN-01 |
| D5 | 现有 `alert` 事件负载 | **只增不改**，保证前端零改动 | ALT-SUB-06 |
| D6 | 与设备失联的关系 | `Telemetry.cc` 的失联判定**保持不动**；本引擎**消费**其结果作为规则输入 | R1 |

## 6. 风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 设备失联判定在 `Telemetry.cc`，与引擎边界相邻 | 双份逻辑 | 明确 D6：`Telemetry.cc` 出"事实"，引擎只做"规则 → 告警" |
| R2 | 告警风暴在 1000 台失联时同时触发 | 界面与推送被打爆 | ALT-DEDUP-06 汇总告警 + ALT-DEDUP-05 抑制关系；实测门槛 |
| R3 | 去重窗口配得过大，把真不同的两次事件合成一条 | 漏警 | 幂等锚点必须是（规则 + **实体**），且窗口按规则分别配置 |
| R4 | 引擎被写成"通用规则引擎" | 配置地狱、与 `topology` 迟滞重复 | 只支持"阈值/持续/组合/恢复 + 去重/抑制"，**不做流式规则语言、不做 CEP** |
| R5 | 告警台账与 `biz-store` 的边界模糊 | 两份存储 | 引擎只管**内存/注入存储**的台账语义；落库归宿主（`biz-store` 的实体定义侧） |
