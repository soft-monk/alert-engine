### 2.1 实测数字（需求关键验收项）

| 验收项 | 实测 |
|---|---|
| **3 秒内触发 10 次 → 一条告警、计数 10**（ALT-GEN-03） | 台账 **1 条**、该条 `count=10`、`firstAt=1000`、`lastAt=3700`（首次时间未被合并修改） |
| **跨窗口触发**（ALT-DEDUP-01） | 窗口 5000ms：t=1000 与 t=4000 归并为 1 条；t=6000 新开第 2 条 |
| **抖动抑制**（ALT-DEDUP-03） | 100 次阈值附近震荡（10.0/10.5 交替）→ 抑制开 **0 条**；同输入抑制关 **100 条** |
| **确认次数 + 最小驻留** | `confirmCount=3`：前 2 次不报、第 3 次报；中途断开则从头累计；`minDwellMs=3000`：满 3000ms 才报 |
| **冷却期不重开** | 关闭后 30s 内复发 → 并入原记录并重新打开（台账仍 1 条、`count` 累加）；冷却期后新开 |
| **触发→恢复→再触发** | 3 条记录：告警(closed) ← 恢复(kind=recovery, `linkedAlertId`) ；第 3 条独立新告警 |
| **升级保留原级别历史** | `levelHistory` 两条 `[warn(created), error(upgraded)]`；`originLevel=warn` 不变；`mergeHistory.upgraded=true` |
| **父子抑制** | 父告警活动时子告警 `suppressed=true`（未产生、未推给订阅者）；父关闭后子告警正常产生 |
| **风暴保护**（ALT-DEDUP-06） | 同一秒 100 条触发（上限 50）→ 新开 **51 条**（50 业务 + 1 汇总）、折叠 **50 条**、汇总 `foldedCount=50`；未启用时同输入 100 条全开 |
| **风暴实战形态**（真实规则包） | 4 线程 400 条同秒触发 → 50 条新开 + 1 条汇总、`foldedCount=350`、`rawRaises=405` 一次不少 |
| **台账截断** | `limit=2` 于 6 条 → `returned=2 / omitted=4 / truncated=true` + 可读原因；`limit=0` → `returned=0 / omitted=total` |
| **确定性** | 覆盖"产生/合并/升级/抑制/风暴/恢复/确认/消音"的序列跑两次，`toJson()` 逐字节一致 |
| **并发** | 8 线程 × 250 条不同实体 → 台账 2000 条、id 唯一；8 × 200 条**同一实体** → 1 条、`count=1600`、`metrics.observations=1600` |
| **性能**（ALT-NFR-06） | 1000 条（1000 条/秒节拍，10 实体轮转）去重+分发：**P50=12.5µs / P95=16.1µs / P99=28.4µs**，合计 12.8ms（P95 ≤ 1ms 达标） |
| **有界台账**（ALT-NFR-07） | 活动上限 2：10 条后 `openActive=3`（上限+本次）、`evicted=7` 如实上报；保留期 500ms/5000ms 对照各一条 |

## 4. 实现说明与相对需求/契约的处置

### 4.1 关键实现决策（机制 vs 业务的分界）

| # | 决策 | 理由 |
|---|---|---|
| D-IMPL-01 | 规则包 `kind:"alertRules"` 用**兄弟段** `levels` / `storm` / `mute`（不新增 `kind`） | 与 protocol §5.3 的 `linkThresholds{nodeTypes,states,hysteresis}`、`entityTypes{numbering}` 同惯例：内容从属于已登记 kind，与之同版本演进 |
| D-IMPL-02 | 恢复判定以**台账记录**上的内部记账 `conditionHeld` 为准，不以本次求值的输出为准 | 首次触发那一刻求值输出必然是"成立"，用它判恢复会立刻误报 |
| D-IMPL-03 | 抖动抑制的连续计数（`confirmCount`/**`minDwellMs`**）**按（规则+实体）跨观测累计**，不因"被抑制"而归零 | 与持续时间计时同理：条件确实连续成立过，计数就应保留；归零会让"确认次数"在高频观测下永远达不到 |
| D-IMPL-04 | `maxGapMs`（持续时间连续性上限）**缺省不限**，需宿主显式声明 | "多长间隔算断档"是宿主采样节拍的性质，不是引擎能猜的业务参数；猜一个缺省会在时钟跳变时静默丢计时。已登记为开放问题 7 |
| D-IMPL-05 | 状态迁移的时间戳取 `IClock`；**自动关闭/恢复**的时间戳取**观测时间** | 自动动作由观测驱动，与持续时间/去重窗口同一时间源，确定性更强（内部台账 `lastAt`/`closedAt` 同源） |
| D-IMPL-06 | 台账有界清扫**按节流周期**执行（保留期与 1s 取小），`tick()` 强制清扫一次 | 1000 条/秒压力下逐条全表扫描会拖慢 P95；节流后 P95 稳定在 16µs |
| D-IMPL-07 | 已关闭告警的 `reopen` 会清空确认/关闭字段（历史一条不少） | "重开"= 新一轮处置；历史由 `stateHistory` 完整承载（`create/acknowledge/close/reopen` 逐条含操作者与时间） |
| D-IMPL-08 | 聚合（风暴汇总）告警的规则 id 为保留值 `$storm`，规则包 MUST NOT 占用 | 与 phase-engine 的 `$` 前缀 gate id 同惯例：保留命名空间，避免与业务规则冲突 |

### 4.2 计数口径（ALT-GEN-05）的一处口径澄清

需求专篇写 `rawRaises == alertsRaised + merged`（针对"10 次触发 → 1 条、计数 10"的场景）。
实现发现该式在**被抑制**（父告警/消音）与**被折叠**（风暴）的路径上不成立 —— 这两类触发
同样是"条件满足的一次触发"，必须计入原始条数。因此引擎采用的恒等式是：

```
rawRaises == alertsRaised + recoveries + merged + folded + suppressed
```

在无抑制/无折叠的纯去重场景下，它与专篇的写法完全一致（`suppressed=folded=0`）。
**属口径澄清，不是冲突**：专篇未涉及这两条路径，且两条口径都在案（`counts` 全字段暴露）。

### 4.3 与需求专篇 §9 / 契约的偏离

**无 MUST 级偏离。** 需求专篇 §9 的 6 项待确认全部变成"参数化 + 开放问题"（见 §5），未擅自选定。

## 5. 仍需人类裁决的开放问题

| # | 问题 | 现状与影响 |
|---|---|---|
| 1 | 告警**级别取值与名称**（"信息/警告/严重"是否够用；要不要"提示"级） | 级别目录已完全参数化（`key/name/rank/color`），规则包给了 3 级；4 级及以上只需改规则包，引擎零改动（ALT-GEN-02 验收"新增一个级别只需改规则"已由 `rule01` 用例锁定） |
| 2 | `alert_count`（风险预警次数）在**报告侧**取哪个口径 | 两种口径同时在案并声明 `basis="deduplicated"`（D7 缺省）；`report-engine` 尚未接线（该仓不在本波） |
| 3 | **首批规则清单**（哪些事件必须报警） | 规则包给了 9 条（8 启用 + 1 默认禁用 `target-hazard-zone`）；属演示集，需产品确认。规则中出现的字段名（`online`/`signal`/`lossRate`/`inHazardZone`/`dangerLevel`/`sensorReading`/`ratePerMin`）需与上游引擎的实际负载字段对齐 |
| 4 | 【告警】页面形态（列表 / 筛选 / 确认按钮 / 历史） | 引擎接口齐备（多维筛选 + 分页 + 截断上报 + 批量活动告警 + 计数口径）；前端未接线 |
| 5 | 是否需要通知渠道（短信/声光/邮件） | 本引擎不做；如需由宿主在 `IAlertSink` 内转发 |
| 6 | 告警是否落 `biz-store` 实体表还是只落事件日志 | 引擎只出 `AlertRecord`（含 `levelHistory`/`mergeHistory`/`stateHistory`）；落库形态由宿主决定 |
| 7 | `maxGapMs` 缺省口径（本实现取"不限"） | 若宿主采样节拍固定，建议在规则里显式给 `maxGapMs`，以把"断档被误判为持续"挡掉 |
| 8 | `alert` 既有事件与新增 `alert.raised/updated/acked` 的**双轨策略** | 本引擎按契约只产出新增的三个（登记在 §4.4）；既有 `alert` 事件名保留。是否由宿主把 `alert.raised` 映射成既有 `alert` 负载，交由宿主决定（前端 `applyWs` 的 `alert` case 零改动的路径已具备） |
